# Preparing 0.11.0

`VERSION` is the release version source. CI checks that the web and desktop
manifests, lockfiles, Rust package, Go build info, and Makefile fallback agree.

## Triggers

- Pushing `main` runs CI, including release configuration regression tests.
- Running `Release` manually with `version=0.11.0` validates credentials and builds
  packages. Results are Actions artifacts; no release assets are published.
- Publishing a GitHub Release tagged `0.11.0` runs the same builds and uploads
  their artifacts to that release. Saving a draft does not trigger publication.

## macOS credentials

Configure these Actions secrets on the repository or in an organization secret
that grants this repository access:

| Secret | Value |
| --- | --- |
| `MACOS_CERTIFICATE` | Base64-encoded PKCS#12 bundle containing the Developer ID Application certificate and private key |
| `MACOS_CERTIFICATE_PASSWORD` | Password for that PKCS#12 bundle |
| `APPLE_ID` | Apple account used for notarization |
| `APPLE_APP_PASSWORD` | App-specific password for that account |
| `APPLE_TEAM_ID` | Team matching the imported certificate |

The workflow does not select a GitHub Environment. Environment-only secrets
therefore are not available to these jobs. Do not place secret values in release
notes or test reports.

The certificate installer requires a valid Developer ID Application identity
matching the team and exports the imported identity to later steps. A separate
`APPLE_SIGNING_IDENTITY` secret is unnecessary. Missing credentials, development
certificates, team mismatches, signature failures, or notarization results other
than `Accepted` stop the workflow.

## Artifact verification

The CLI launcher embeds the signed `bluecli`. Both executables are verified and
submitted together for notarization; the distributed archive contains the
self-extracting launcher. The desktop workflow signs the final app and DMG,
requires accepted notarization, staples the DMG, and checks the signature,
stapled ticket, and Gatekeeper assessment. `lipo` checks the intended architecture
for both CLI executables and the desktop executable.

Local signing tests mock Apple tooling. They verify failure handling and identity
propagation, but do not establish that an artifact has a trusted signature.
Before publication, inspect a successful manual Release run for this exact
commit, download both macOS architectures, and retain the signing/notarization
logs. Then remove the preparation notice from the release body.

Existing execution Harness evidence applies to the unchanged execution sources.
It must not be described as a fresh gate result for the 0.11.0 binary.

## Local verification

The candidate passed `go test -tags fts5 ./... -count=1 -timeout 5m` across
173 test-bearing packages, without additional test exclusions. Release regression
tests (19), raw-builder tests (1), frontend locale/renderer regressions (25), the
frontend production build, strict i18n audit, and actionlint also passed. The
updated frontend lockfile reported zero npm audit vulnerabilities. Earlier
failures and the disk-space recovery run remain recorded in local test evidence;
only the subsequent complete successful run is treated as the final Go result.
