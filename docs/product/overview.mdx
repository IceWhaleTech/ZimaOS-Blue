# Overview

ZimaOS Blue is an open-source, auditable runtime for building and operating local-first AI agents across personal and team environments.

![Design principles](/design_principle.png)

## Core product position

- **Local-first**: run on your own hardware and network boundaries
- **Lightweight**: written in Go and designed for low runtime overhead
- **Cross-device**: intended for desktop, server, NAS, edge, and Raspberry Pi style deployments
- **Composable**: combine chat, voice, automation, memory, evaluation, and tools without locking into one provider

## What teams actually use it for

Blue is not just a model wrapper. In the current product shape, teams typically use it to:

- Stand up a private chat and voice assistant on hardware they already control
- Connect that same runtime to channels, browser tasks, and automation triggers
- Route between cloud APIs, local small models, and external agents without rewriting the app surface
- Evaluate prompts, skills, and workflows with Harness before promoting or rolling them out more broadly
- Keep security, auth, sandbox, audit, billing, and tenant concerns inside the same operator surface

## What Blue includes

- Gateway and server layers for runtime orchestration
- Provider pool, model routing, and external-agent connectivity
- Context, memory, tooling, and personality layers for agents
- Channel integrations for messaging and remote interaction
- Security, auth, sandboxing, audit, billing, and tenant controls
- Voice, browser, workflow, form-filling, and automation capabilities
- Harness and Evolution surfaces for tracked execution, scoring, and skill iteration
- Skills, skill-store discovery, and tool catalog surfaces for extensibility

## Ecosystem reach

![Channel, provider, and IDE ecosystem](/providers.png)

The runtime is designed to stay open at the edges:

- Messaging and social channels can plug into one shared runtime core
- Providers stay mix-and-match instead of forcing one model vendor
- Coding assistants and external agents can be treated as first-class participants instead of side tools
- Local models and cloud models can coexist in one operator workflow

## Why teams reach for it

The current product shape emphasizes five operator promises:

- Fast zero-to-one setup
- Rapid prototyping for scenario-specific agent products
- Evaluatable and auditable execution instead of black-box orchestration
- Multi-language reach
- Open model ecosystem without vendor lock-in

## What stays consistent across the product

Even when you move between chat, voice, channels, automation, and evaluation, a few things stay consistent:

- The same provider-routing and model-selection layer
- The same security, permission, and audit posture
- The same runtime core for tools, memory, and agent behavior
- The same operator-facing web surface for setup, visibility, and governance
