# Deployment

ZimaOS Blue docs are prepared for **GitHub Pages deployment through GitHub Actions**.

## What this repository already provides

- Docusaurus site runtime files inside `docs/`
- Site config in `docs/docusaurus.config.ts`
- Sidebar and root-link compatibility plugin in `docs/sidebars.js` and `docs/plugins/remark-root-links.cjs`
- Docs content, runtime, and shared images kept together in `docs/`
- Static image assets directly reused from `docs/assets`
- Local build validation from inside `docs/`
- CI build plus Pages deployment on docs-related changes to `main`

## Recommended deployment model

The repository now follows this model:

1. Open the repository's `Settings -> Pages`
2. Set `Build and deployment` to `GitHub Actions`
3. Keep the publishing branch as `main`
4. Let `.github/workflows/docs.yml` build and deploy the site
5. Optionally bind a custom docs domain later

## Why the workflow looks this way

This repo intentionally builds a static site inside GitHub Actions and publishes the generated `build` artifact through the official GitHub Pages actions:

- `actions/configure-pages`
- `actions/upload-pages-artifact`
- `actions/deploy-pages`

That keeps the deployment path explicit, reviewable, and independent from any external hosted docs platform.

## Repository layout that Pages expects

This repo intentionally keeps the whole docs site under one directory:

- Docusaurus runtime files live in `docs/`
- Published pages are sourced from the same `docs/` directory
- Shared images stay in `docs/assets`
- `docs/plans` and `docs/results` are not part of the published docs include list
- There is no separate `docs-site/` app to maintain

That layout matters because the GitHub Actions workflow now resolves the Docusaurus config from `docs/`, installs dependencies there, and uploads `docs/build` to Pages.

## Pre-deploy checklist

Before enabling or re-running deployment, confirm:

- `cd docs && npm ci` succeeds
- `cd docs && npm run build` succeeds
- `cd docs && DOCUSAURUS_URL=https://IceWhaleTech.github.io DOCUSAURUS_BASE_URL=/ZimaOS-Blue/ npm run build` succeeds
- Repository `Settings -> Pages` is set to `GitHub Actions`
- The navbar links point to the correct GitHub, Releases, and DeepWiki URLs
- The default branch contains the latest docs content

## Local validation

```bash
cd docs
npm ci
npm run build
DOCUSAURUS_URL=https://IceWhaleTech.github.io DOCUSAURUS_BASE_URL=/ZimaOS-Blue/ npm run build
```

## If Pages shows a README-like page or 404

That usually means GitHub Pages did not publish the Docusaurus build artifact at all, not that `docs/` content is wrong.

Check these first:

- `docs/docusaurus.config.ts`, `docs/sidebars.js`, and `docs/plugins/remark-root-links.cjs` exist on the default branch
- `Settings -> Pages -> Build and deployment` is set to `GitHub Actions`
- The `Docs` workflow actually runs `build` and `deploy` instead of skipping after config resolution
- The public Pages URL `https://icewhaletech.github.io/ZimaOS-Blue/` is opened after the latest deploy finishes

## Suggested rollout order

- Enable GitHub Pages for the repository
- Push or merge docs changes into `main`
- Verify the published English root and `/zh-CN/` pages
- Add a custom docs domain later if needed
- Replace repository-relative docs links in `README.md` with the public docs URL once the domain is live

## After docs updates land

For routine content updates like new product guides or navigation changes:

1. Run `cd docs && npm run build`
2. Verify English and Simplified Chinese navigation stay aligned where mirrors exist
3. Open or update the pull request and let CI build the site
4. Merge to `main` and let GitHub Pages deploy automatically
