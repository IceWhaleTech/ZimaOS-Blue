# Providers and Models

Blue uses a provider pool so model access, routing, and failover stay in one operator surface instead of being scattered across the product.

![Provider inventory and routing overview](/providers.png)

## What you can control from the provider pool

The current provider-pool UI and API support more than "add a key and hope it works." In practice, operators can work with:

- A default provider
- Multiple provider types such as `trial`, `builtin`, `platform`, `custom`, and `media`
- Routing priority
- `cloud` or `local` location metadata
- API compatibility format selection
- Provider verification
- Model refresh
- Allowed-model restrictions
- Pricing and capability metadata
- Health-check, failover, and provider-racing behaviors in the broader routing layer

## What a custom provider actually contains

The custom-provider flow in the current web app exposes these core fields:

- Provider name
- Base URL
- API key
- Routing priority
- API format such as `auto`, `openai`, `responses`, `anthropic`, or `google`
- Location set to `cloud` or `local`

That makes the same Blue runtime flexible enough to talk to hosted APIs, internal gateways, and local compatibility endpoints without rewriting the rest of your app.

## A safe operator order for adding a provider

When you are onboarding a new provider, the least confusing sequence is:

1. Save the provider with the correct endpoint, credentials, location, and API format.
2. Run verification before making it your default route.
3. Review the detected or recommended API format if verification suggests a better fit.
4. Refresh the model catalog.
5. Restrict allowed models only after you know the catalog is correct.
6. Set the provider as default if it is meant to carry normal traffic.
7. Run a real chat smoke test.

This separates "the record exists" from "the route really works."

## What verification is for

Verification is not just a yes-or-no ping. The current verification result can surface:

- The base URL Blue actually tested
- A model used for the probe
- Detected API format
- Recommended API format
- Recommended base URL
- Whether the endpoint behaves like a `responses`-only surface
- Per-probe reachability and status details

That means verification can catch problems such as:

- Wrong endpoint shape
- Wrong compatibility format
- A reachable host that still does not behave like the provider type you expected

## Model inventory and control

Once a provider exists, model management becomes the next operator step. The current product supports:

- Refreshing the provider's remote model catalog
- Viewing model capabilities
- Seeing pricing fields such as input, output, cache, or per-request cost where available
- Reviewing context window and max-output metadata
- Restricting allowed models so routing only uses approved entries

This is where many rollout mistakes happen. A provider may verify correctly but still fail normal usage if the expected model is absent, disabled, or accidentally filtered out.

## How to think about `cloud` and `local`

The `cloud` versus `local` setting is worth filling correctly because it improves the operator view later.

- Use `cloud` for hosted APIs and remote gateways
- Use `local` for runtimes or compatibility layers on the same machine or local network

This is especially useful when you are comparing:

- Latency expectations
- Failure domains
- Privacy posture
- Deployment topology

## Routing, failover, and provider racing

Blue's routing layer is designed so provider choice is not a one-time hardcoded decision. The current docs and config surface support:

- A default provider
- Ordered provider preference
- Health checks
- Failover and recovery controls
- Optional provider racing for parallel attempts

Operationally, that means you can use the provider pool for more than first setup. It also becomes the control plane for resilience, migration, and cost balancing over time.

## What a healthy provider setup looks like

You are usually in a good state when all of the following are true:

- The provider saves successfully
- Verification succeeds
- The recommended API format and base URL match what you intended, or you deliberately change them
- The model list refreshes correctly
- Allowed-model restrictions are deliberate
- The provider can serve a real chat request

If one of those is missing, stop there before adding more providers or tuning routing policy.

## Common operator questions

| Question | Where to focus |
| --- | --- |
| "Did I point Blue at the right endpoint?" | Provider verification result |
| "Why does the provider save but still fail chat?" | API format, model refresh, and allowed models |
| "Which provider should carry normal traffic?" | Default provider plus routing priority |
| "How do I separate local and hosted capacity?" | `location` metadata and provider ordering |
| "How do I keep unsafe or unwanted models out of rotation?" | Allowed-model controls |
