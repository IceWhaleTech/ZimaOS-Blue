# Providers and Models

ZimaOS Blue is designed around an open provider ecosystem.

## Provider pool basics

Blue centralizes model access through a provider pool instead of scattering vendor-specific setup across the product. The current UI and server config expose:

- A default provider
- Multiple providers in a sorted routing order
- Health checks per provider
- Failover settings with retry and recovery controls
- Optional provider racing for parallel attempts
- Cloud or local location metadata
- Provider-specific model refresh and verification actions

## Provider types you will see in the UI

- Built-in providers for common hosted APIs
- Platform and trial providers exposed by the runtime
- Custom providers you add manually with a base URL and key
- Media-oriented providers for speech or multimodal flows

The provider pool page groups these categories into tabs so operators can keep routing changes in one place.

## What a custom provider can carry

The custom-provider flow in the web app supports:

- Provider name and base URL
- API key
- Routing priority
- API compatibility format such as `auto`, `openai`, `responses`, `anthropic`, or `google`
- Cloud or local location metadata

After creation, operators can verify the provider, refresh models, review pricing, and control allowed models.

## Model routing

Blue supports model families and fallback patterns. In practice this means Blue can:

- Match a requested model name to a provider family
- Send the request to the right upstream provider
- Fall back to a safer or cheaper sibling model when configured
- Keep provider choice separate from the rest of the app's product logic

## Verification and control loops

The current provider surface is not only about static config. Operators can also:

- Verify a provider before trusting it in production traffic
- Refresh remote model inventories
- Restrict which models are eligible for routing
- Inspect provider pricing and metadata
- Use IDE or runtime discovery helpers where supported

## Why this matters

- You can separate product behavior from a single vendor contract
- Teams can trade off latency, price, capability, and resilience
- One runtime can support experimentation, failover, and migration paths over time
