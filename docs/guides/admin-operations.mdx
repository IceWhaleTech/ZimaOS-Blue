# Admin and Operations

Blue's operator story is now spread across several real pages, not one hidden admin panel. The easiest way to use it well is to know which page answers which question.

## Which page should you open?

| If you need to answer... | Open |
| --- | --- |
| "Is the runtime healthy right now?" | `Home` |
| "What security controls or exposure should I review?" | `Security` |
| "What happened, and who changed what?" | `Audit` |
| "Which provider or model is driving cost or anomalies?" | `Billing` |
| "How do I create or manage workspaces?" | `Tenants` |
| "How do I manage one workspace's members or limits?" | `Tenant Detail` |
| "How do people sign in?" | `Auth Providers` and [Identity and Access](/guides/identity-access) |
| "How do I manage users?" | `Users` plus profile and auth flows |

## Home: first stop for runtime health

The `Home` page acts as a lightweight operator dashboard. The current implementation can surface:

- System status
- Uptime
- CPU, memory, and goroutine cards
- Refreshable runtime-metric history
- Optional OS, hardware, runtime, disk, GPU, and network details

Open this page first when you want to know whether the runtime is broadly healthy before you start debugging providers, auth, or workflow behavior.

## Security: where hardening work actually happens

The current `Security` view is organized into four tabs:

- `Overview`
- `Controls`
- `Monitoring`
- `Logs`

Together these tabs cover:

- Active sessions and revocation
- Threat stats and recent threat events
- Security scans with fix preview and fix execution
- Prompt firewall configuration
- CORS, TLS, and ACME status
- Sandbox runtime information and network toggle
- Tool approval policy
- Approved directories and approved browser sites
- Directory whitelist behavior

Use this page when you are preparing for production, tightening sandbox or approval policy, or reviewing whether a deployment is more open than intended.

## Audit: use it for "what happened?"

The audit page is the right answer when you need event history rather than current state. It currently supports:

- Filtered audit entries
- Status and action breakdowns
- Time-window filtering
- Export to JSON or CSV

That makes it the right page for incident review, change tracking, and postmortem evidence collection.

## Billing: usage analysis, not just totals

The current `Billing` page is a usage-observability surface. It supports:

- Date-range filters
- Provider and model filters
- `group_by` views such as day, provider, or model
- Success-rate summaries
- Token and cost trend charts
- Line-item views
- CSV export
- Anomaly drilldown for usage spikes

In other words, `Billing` is where you answer questions like:

- Which provider is getting expensive?
- Which model is seeing the highest request volume?
- Did usage spike on a specific day?
- Is a cost jump tied to one provider, one model, or a broader traffic change?

## Tenants: workspace lifecycle entry point

The `Tenants` page is where workspace governance starts. The current page includes:

- Create workspace
- Edit workspace
- Select workspace
- Open a direct `Manage` action
- Delete a workspace when permitted
- Status, slug, description, and created-date visibility

Use this page when you are onboarding a new team, segmenting environments, or cleaning up old workspaces.

## Tenant Detail: where ongoing workspace administration lives

Once you open a specific tenant, the current `Tenant Detail` surface is split into four tabs:

- `Members`
- `Invitations`
- `Settings`
- `Limits` for owners

Those tabs let operators handle:

- Member role changes
- Invite and revoke flows
- Default workspace language
- Workspace timezone
- Owner-visible limits such as max users, storage, API requests, workflows, and channels

Use `Tenants` to find the workspace. Use `Tenant Detail` to actually administer it.

## Auth Providers and Users: identity rollout layer

Blue's identity surfaces are now large enough that they should be treated as an operator area, not a side setting. The current product includes:

- Auth-provider management for OIDC-style and common hosted identity providers
- Callback-based sign-in flows
- Preview bootstrap and first-admin upgrade flow
- User administration for lock, unlock, reset-password, and permission operations
- Profile-level linked accounts, API keys, MFA, and WebAuthn

When the real question is "who can get in, and how?", continue with [Identity and Access](/guides/identity-access).

## A practical day-two operator order

1. Open `Home` to confirm runtime health.
2. Check `Security` before broad rollout.
3. Use `Audit` to confirm you can trace important actions.
4. Watch `Billing` once real traffic starts.
5. Set up `Tenants` and `Tenant Detail` when more than one team or workspace is involved.
6. Finish `Auth Providers`, `Users`, and identity policy before wider onboarding.

## Common routing mistakes

- Looking in `Billing` for incident history that really belongs in `Audit`
- Treating `Tenants` as the full workspace-admin surface instead of the entry into `Tenant Detail`
- Trying to debug sign-in issues from general security controls before checking auth-provider setup
- Skipping `Home` and going straight into deeper settings when the runtime itself may not be healthy
