# Settings and Provider Pool

The settings area is now the main operator surface for configuring Blue's runtime, not just a small preferences page.

![Provider and runtime setup surface](/demo%20Provider.gif)

## Settings tabs at a glance

The current app groups settings into five tabs:

- `General`: language, theme, device behavior, network entry, and update flow
- `LLM`: provider pool, model routing, and external agent connectivity
- `Proxy`: request-routing helpers and lightweight runtime behavior
- `Speech`: speech input, output, and voice pipeline preferences
- `User Data`: memory, export, backup, and restore flows

## Shortest provider-setup path

If your goal is simply "make the first real response work," this is the shortest UI path:

1. Open `Settings`.
2. Switch to the `LLM` tab.
3. Add one provider you actually plan to use.
4. Fill in the endpoint, credentials, compatibility format, and `cloud` or `local` location.
5. Run provider verification before trusting it.
6. Refresh the model catalog if needed.
7. Pick the default provider.
8. Restrict allowed models if you want tighter routing.
9. Return to chat and run a smoke test.

## Provider pool basics

The provider pool is the current control plane for model access. In the UI you can:

- Browse providers by type such as built-in, platform, custom, trial, and media
- Pick a default provider
- Drag-sort providers to control routing preference
- Verify providers before trusting them in production traffic
- Refresh provider model inventories
- Inspect pricing or capability metadata where available

## What a healthy first provider setup looks like

You are usually in a good state when all of the following are true:

- The provider record saves successfully
- Verification succeeds against the endpoint you intended
- The model list refreshes or is already present
- The default provider matches your expected route
- Allowed-model restrictions, if any, are deliberate rather than accidental
- A simple chat prompt returns successfully

## Adding a custom provider

The custom-provider flow supports more than a base URL and key. You can set:

- Provider name
- Base URL
- API key
- Routing priority
- API compatibility format such as `auto`, `openai`, `responses`, `anthropic`, or `google`
- Location metadata to mark a provider as `cloud` or `local`

These fields make it easier to run the same Blue runtime against hosted APIs, local gateways, or compatibility layers without rewriting the rest of your product.

## Cloud versus local location

Blue lets you label providers as `cloud` or `local` in the settings UI.

- Use `cloud` when requests go to a hosted API or remote gateway
- Use `local` when the model runtime or compatibility endpoint lives on your own machine or local network

This does not just improve readability. It also makes the operator surface easier to reason about later when you are comparing latency, failure domains, or deployment shape.

## Minimum custom-provider checklist

Before opening `Add provider`, prepare these minimum values:

- A provider display name
- A reachable base URL or endpoint
- An API key or bearer token
- The compatibility format Blue should speak, such as `openai`, `responses`, `anthropic`, or `google`
- Whether the endpoint should be treated as `cloud` or `local`
- The exact model names you want to allow, if you plan to restrict them

A simple operator worksheet can look like this:

```text
Name: OpenAI Prod
Base URL: https://api.openai.com
API key: <secret>
Format: responses
Location: cloud
Allowed models: gpt-4.1, gpt-4o-mini
```

If you prefer config-first rollout, the checked-in example config already shows the minimal routing shape:

```yaml
proxy:
  routing:
    default_provider: "openai"
    providers:
      - name: "openai"
        endpoint: "https://api.openai.com"
        api_key: "${OPENAI_API_KEY}"
        priority: 1
        enabled: true
        health_check: "/v1/models"
```

The settings UI can carry richer state than this minimal snippet, including compatibility format, location metadata, verification results, and allowed-model controls.

## Recommended order inside the UI

When you are configuring a provider from scratch, the least confusing order is:

1. Save the provider with the right endpoint and credentials
2. Verify the provider before making it default
3. Refresh the model inventory
4. Review allowed models
5. Set it as the default provider

This keeps "it saved" separate from "it actually works."

## Model controls

After a provider is connected, Blue can expose:

- Allowed-model controls so you can limit which models the app may route to
- Verification results before enabling a provider for normal traffic
- IDE or runtime discovery helpers where supported
- Per-provider model refresh so you do not need to restart the whole app to pick up upstream catalog changes

For the routing behavior itself, continue with [Providers and Models](/guides/providers-models).

## Common first-pass mistakes

- Saving a provider but never running verification
- Using the wrong compatibility format for the upstream API
- Forgetting to refresh models after changing the endpoint
- Accidentally over-restricting allowed models and then assuming the endpoint is broken
- Making a provider default before you know it works

## External agents

Blue can also manage external agent profiles from the settings surface. The current implementation supports:

- ACP and A2A style profiles
- Built-in or template profiles
- Command, working-directory, and environment overrides for ACP profiles
- Endpoint URL and header wiring for remote-style profiles
- Credential-provider and auth-method attachment
- Verify and health-check actions before you rely on the profile

This is useful when Blue needs to coordinate with a coding agent, research agent, or another runtime without collapsing everything into one monolith.

Blue already exposes a real external-agent control plane behind this settings flow. In practice that means:

- The web app can manage external agent profiles
- The service can create, message, cancel, close, and stream external agent sessions
- The `blue agent-sessions` CLI can operate the same surface from the terminal

### ACP command defaults

Blue's built-in ACP templates now default to binary-first commands:

- Claude: `claude-agent-acp`
- Codex: `codex-acp`
- Gemini: `gemini --acp`

That means:

- If the adapter binary is already on `PATH`, Blue uses it directly
- For Codex, that works well with downloaded release binaries or other direct installs
- For Gemini, the CLI already exposes ACP mode directly through `gemini --acp`
- For Claude and Codex, Blue still preserves the existing npm fallback when the binary is missing

Current fallback behavior:

- `claude-agent-acp` falls back to `npx -y @zed-industries/claude-agent-acp`
- `codex-acp` falls back to `npx @zed-industries/codex-acp`

Operationally, this means you can prefer direct binaries or globally installed commands, while still keeping older npm-based setups working.

## Using Agentcore Runner as a Blue-facing ACP or A2A bridge

If you want to put the protocol boundary on `agentcore-runner`, the current repository now supports that directly.

Build the runner from the server module:

```bash
cd server
go build ./cmd/agentcore-runner
```

Run ACP mode and point it at Blue:

```bash
./agentcore-runner acp --blue-url http://127.0.0.1:18080
```

Run A2A mode and expose an HTTP endpoint backed by Blue:

```bash
./agentcore-runner a2a --listen 127.0.0.1:7788 --blue-url http://127.0.0.1:18080
```

If your Blue deployment needs extra headers such as bearer auth, add one or more `--blue-header` flags:

```bash
./agentcore-runner acp \
  --blue-url http://127.0.0.1:18080 \
  --blue-header "Authorization=Bearer <token>"
```

Current bridge behavior:

- The first prompt creates a Blue conversation and later prompts reuse it
- Blue's streaming message deltas are forwarded through ACP `session/update` or A2A `message/stream`
- Cancel requests are forwarded back to Blue's conversation cancel endpoint
- If you omit `--blue-url`, the runner keeps its default local stub behavior for testing and harness workflows

Use this pattern when you want Blue to remain the conversation runtime, but another system expects an ACP process or an A2A HTTP endpoint at the edge.

## Speech, memory, and recovery

Settings is also where Blue collects the day-two controls that usually get scattered across smaller apps:

- Speech preferences and voice pipeline behavior
- Memory recall mode and user-data export
- Backup creation, restore, and deletion
- General runtime behaviors such as update and service settings

## Recommended operator path

If you are setting up a new Blue deployment, this sequence is usually the shortest path:

1. Finish installation and open the web app
2. Configure providers and verify the ones you plan to use
3. Restrict or review allowed models if needed
4. Add any external agents Blue should coordinate with
5. Set speech, memory, and backup preferences before sharing the system with more users
