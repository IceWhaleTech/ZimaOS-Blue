# v0.10.32 Deep Research 设计方案（Draft）

## 1. 目标与范围

目标：在 ZimaOS-Blue 内新增“深度搜索（Deep Research）”能力，支持从单轮问答升级为“多轮规划 + 并行检索 + 证据整合 + 可信度评估 + 可追溯引用”的完整链路。

本期范围：
- 支持 Web + 已有技能数据源（如 browser/search/analyze）协同检索
- 支持多阶段任务分解与并行执行
- 支持结构化证据存储、去重、打分、冲突检测
- 支持流式回传（进度、阶段结论、最终报告）
- 支持预算/时延/深度控制（快搜、标准、深搜）

非目标（首版不做）：
- 通用网页爬虫平台化（大规模抓取调度）
- 长期知识库自动构建（离线索引系统）
- 全自动发布级报告排版引擎（先输出 Markdown/JSON）

## 2. 设计理念（参考 mirothinker / miroflow）

结合两类理念做落地抽象：

- `Thinker`：先思考再执行。将“问题分解、假设生成、验证路径”独立成 Planner，不与抓取执行耦合。
- `Flow`：把研究过程变成可观测的 DAG 流程，节点可重试、可并行、可中断恢复。

在本项目中的映射：
- 使用现有 `server/internal/workflow` 作为执行编排底座（DAG + 状态 + 执行日志）
- 新增 `deepresearch` 领域层，负责“研究语义”而非通用流程编排

## 3. 总体架构

```text
User Query
  -> DeepResearch Service
    -> Planner (query decomposition / hypothesis)
    -> Workflow Builder (DAG compile)
    -> Executor (reuse workflow engine)
      -> Search Node (web/search skill)
      -> Fetch Node (browser/extract)
      -> Read Node (content normalize/chunk)
      -> Score Node (relevance/credibility/novelty)
      -> Verify Node (cross-source contradiction check)
      -> Synthesis Node (LLM summarize with citations)
    -> Evidence Store (SQLite JSON + indices)
    -> Stream Hub (SSE/WebSocket progress)
  -> Final Report (answer + citations + confidence + gaps)
```

## 4. 模块拆分（建议新增）

建议目录：
- `server/internal/deepresearch/service.go`
- `server/internal/deepresearch/planner.go`
- `server/internal/deepresearch/dag_builder.go`
- `server/internal/deepresearch/executor.go`
- `server/internal/deepresearch/evidence_store.go`
- `server/internal/deepresearch/scorer.go`
- `server/internal/deepresearch/verifier.go`
- `server/internal/deepresearch/types.go`
- `server/internal/deepresearch/handler.go`

核心职责：
- `Service`：任务生命周期（创建、取消、查询、流式事件）
- `Planner`：将用户问题拆分为研究子任务（子问题、关键词、数据源策略）
- `DAGBuilder`：把计划编译为 workflow 节点图
- `Executor`：调用 workflow 引擎执行并收集节点结果
- `EvidenceStore`：统一保存证据（来源、时间、片段、置信度）
- `Scorer`：相关性、可信度、去重分数
- `Verifier`：跨来源一致性与冲突检测

## 5. 数据模型（核心）

`DeepResearchJob`
- `id`
- `query`
- `mode` (`fast|standard|deep`)
- `status` (`pending|running|synthesizing|completed|failed|cancelled`)
- `budget` (`max_steps|max_sources|max_tokens|max_seconds`)
- `created_at|updated_at|completed_at`

`ResearchTask`
- `id`, `job_id`
- `question`（子问题）
- `priority`
- `depth`（层级）
- `status`

`Evidence`
- `id`, `job_id`, `task_id`
- `source_url`, `source_type`, `domain`
- `published_at`, `fetched_at`
- `title`, `snippet`, `raw_text_ref`
- `relevance_score`, `credibility_score`, `novelty_score`
- `claim_hash`（用于去重/冲突聚类）

`SynthesisResult`
- `job_id`
- `answer_markdown`
- `citations[]`（证据 ID + URL）
- `confidence`（0-1）
- `open_questions[]`

## 6. 执行流程（状态机）

1. `Intake`
- 规范化 query，识别任务类型（事实问答/比较研究/方案调研）

2. `Plan`
- 生成研究计划：子问题、优先级、停止条件

3. `Retrieve`
- 并行搜索（关键词变体 + 数据源策略）

4. `Expand`
- 对高价值结果进行二跳扩展（引用追踪/关联主题）

5. `Evaluate`
- 去重、评分、过滤低质量来源

6. `Verify`
- 对关键结论做交叉验证与冲突标注

7. `Synthesize`
- 产出带引用答案、置信度与未解问题

8. `Finalize`
- 存档执行日志和证据图谱，支持复盘

## 7. 与现有系统的集成点

1. `workflow` 引擎复用
- 复用 DAG 执行、并发、超时、日志、重试能力
- deepresearch 仅新增 action handler，不重写引擎

2. `skill` 复用
- 首版优先调用现有 `search`、`browser`、`analyze` 链路
- 减少重复实现

3. `proxy` 与模型路由
- 综合阶段可复用现有多 Provider/HA 路由
- 对 `deep` 模式可配置更高质量模型与更高 token 上限

## 8. API 设计（首版建议）

`POST /api/v1/deep-research/jobs`
- 入参：`query`, `mode`, `budget`, `lang`
- 出参：`job_id`, `status`

`GET /api/v1/deep-research/jobs/:id`
- 返回 job 状态、阶段进度、初步结论

`GET /api/v1/deep-research/jobs/:id/events` (SSE)
- 事件：`job_started`, `task_planned`, `evidence_added`, `conflict_found`, `partial_answer`, `job_completed`

`POST /api/v1/deep-research/jobs/:id/cancel`
- 中断执行

`GET /api/v1/deep-research/jobs/:id/report`
- 返回最终报告（Markdown/JSON）

## 9. 质量与安全策略

- 预算守卫：步骤数、来源数、token、总时长硬限制
- 来源白/黑名单：可按域名策略过滤
- 时间敏感任务优先新鲜度（按 `published_at` 加权）
- 引用强制：关键结论必须有证据绑定
- 冲突提示：结论存在冲突来源时显式标注“待确认”
- 失败降级：检索失败时回退到“有限来源总结”而非直接失败

## 10. 里程碑计划

M1（可用版，1-2 周）
- Job API + 状态机
- Planner v1（单层子问题分解）
- Search/Retrieve + EvidenceStore + 基础引用输出

M2（增强版，1-2 周）
- 二跳扩展（Expand）
- Scorer（相关性 + 可信度）与去重
- SSE 流式事件与中间结论回传

M3（完整版，2 周）
- Verifier（冲突检测 + 交叉验证）
- 深度模式预算策略
- 回放与复盘（执行图 + 证据链）

## 11. 测试策略

单测：
- planner 分解稳定性（同输入同结构）
- scorer 打分边界与去重
- verifier 冲突识别准确性

集成测试：
- `job create -> run -> report` 全链路
- 中断与恢复
- 预算耗尽后的安全退出

回归测试：
- 不影响现有 workflow / proxy / skill 的行为
- 模型不可用时的降级路径

## 12. 风险与权衡

- 风险：检索源质量不稳定导致“看似完整但证据薄弱”
  - 对策：强制置信度与证据密度阈值，不足时输出“不确定”

- 风险：深搜模式成本高、耗时长
  - 对策：默认 `standard`，`deep` 显式开启且受预算控制

- 风险：与通用 workflow 职责边界模糊
  - 对策：workflow 只做执行，deepresearch 持有研究语义

## 13. 首批实现建议（最小闭环）

先做这一条链路即可上线试用：
- `POST job`
- planner 产出 3-5 个子问题
- 并行 web search + topN 抓取
- 证据去重打分
- 带引用总结 + 置信度
- SSE 实时进度

这能在不大改现有架构的前提下，形成“深度搜索”可感知能力；后续再叠加冲突验证与更复杂工作流。
