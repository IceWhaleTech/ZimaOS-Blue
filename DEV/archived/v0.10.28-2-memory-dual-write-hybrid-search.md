# PRD v0.10.28-2: 记忆双写 + 混合搜索恢复（语义检索 + 全文检索）

**版本**: 0.10.28-2
**状态**: Draft
**前置**: v0.10.28 memory service (已部分删除于 fd20f26)

---

## 背景

fd20f26 提交中删除了记忆系统的核心组件：
- `embedding/` 包（OpenAI/Ollama embedding provider + cache）
- `memory/vector_store.go`（SQLite 向量存储 + FTS5）
- `memory/hybrid_search.go`（混合搜索：向量 + 关键词）
- `memory/dual_write_backend.go`（双写后端）
- 以及 progressive_search、session_hook、memory_refresher 等

当前状态：仅剩 `PureMarkdownBackend`（纯关键词搜索），无语义检索能力，搜索质量差。

## 目标

1. **双写架构**：写入时 Markdown 为主（人类可读），异步写入 SQLite（向量 + FTS5）
2. **混合搜索**：语义检索（sqlite-vec cosine）权重 0.7 + 全文检索（FTS5 BM25）权重 0.3
3. **Rerank 阈值**：综合分数 > 0.5 的结果取 top-K 返回
4. **sqlite-vec**：使用 CGo binding（`sqlite_vec.Auto()`），int8 标量量化（4x 压缩，~15MB/10K 条）
5. **SQL 层融合**：FTS5 + sqlite-vec 在同一 SQLite DB，rowid 对齐，SQL 层直接做分数融合

## 架构设计

### 存储结构

FTS5 和 sqlite-vec 在同一个 SQLite 数据库中，通过 rowid 对齐：

```sql
-- 元数据表（主表）
CREATE TABLE memory_chunks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    chunk_id TEXT UNIQUE NOT NULL,     -- 外部 ID (mem_xxxx)
    content TEXT NOT NULL,
    tags TEXT,                          -- JSON array
    metadata TEXT,                      -- JSON object
    importance REAL DEFAULT 0.5,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL
);

-- FTS5 全文索引（rowid 对齐 memory_chunks.id）
CREATE VIRTUAL TABLE memory_fts USING fts5(
    content,
    tags,
    content=memory_chunks,
    content_rowid=id,
    tokenize='porter unicode61'
);

-- sqlite-vec 向量索引（rowid 对齐 memory_chunks.id，int8 标量量化）
CREATE VIRTUAL TABLE memory_vec USING vec0(
    embedding int8[1536]     -- int8 量化：4x 压缩，~15MB/10K 条，精度损失 ~1-3%
);
```

### 写入路径

```
Remember(content, tags) →
  ├─ PureMarkdownBackend.Remember()     [主，同步，source of truth]
  └─ VectorStore.Store()                [副，异步 goroutine]
       ├─ INSERT INTO memory_chunks     (元数据)
       ├─ INSERT INTO memory_fts        (FTS5 索引，触发器自动)
       ├─ EmbeddingProvider.Embed()     (生成 float32 向量，有缓存)
       ├─ vec_quantize_i8(embedding)   (float32 → int8 量化，sqlite-vec 内置)
       └─ INSERT INTO memory_vec        (int8 量化向量，rowid 对齐)
```

### 搜索路径

**方案三：SQL 层混合分数融合**（推荐，单次查询完成）

```sql
-- 语义检索 + 全文检索 + 分数融合，一条 SQL
WITH vec_results AS (
    SELECT rowid, distance
    FROM memory_vec
    WHERE embedding MATCH ?       -- query embedding
    ORDER BY distance
    LIMIT ?                       -- limit * 3 候选
),
fts_results AS (
    SELECT rowid, rank
    FROM memory_fts
    WHERE memory_fts MATCH ?      -- query text
    LIMIT ?                       -- limit * 3 候选
)
SELECT
    c.chunk_id, c.content, c.tags, c.metadata,
    c.importance, c.created_at, c.updated_at,
    COALESCE(1.0 - v.distance, 0) AS vector_score,
    COALESCE(-f.rank, 0) AS keyword_score,
    COALESCE(1.0 - v.distance, 0) * 0.7 + COALESCE(-f.rank, 0) * 0.3 AS combined_score
FROM memory_chunks c
LEFT JOIN vec_results v ON v.rowid = c.id
LEFT JOIN fts_results f ON f.rowid = c.id
WHERE v.rowid IS NOT NULL OR f.rowid IS NOT NULL
HAVING combined_score > 0.5
ORDER BY combined_score DESC
LIMIT ?;
```

对于数据量 > 10K 的场景，推荐先 FTS 过滤再 vec 排序：

```
FTS 先过滤（精确匹配缩小范围）→ vec 再排序（语义相似度）→ Go 层 ImportanceScorer rerank
```

### 降级路径

```
Level 1 (完整): sqlite-vec 语义搜索(0.7) + FTS5 全文搜索(0.3) → SQL 层融合
  ↓ embedding provider 不可用（无 API key / 网络不通）
Level 2 (部分): FTS5 全文搜索 only（仍走 SQLite）
  ↓ SQLite/VectorStore 初始化失败
Level 3 (基础): 纯 Markdown 关键词搜索（现有行为）
```

## 高可用设计

### HA-1: 异步写入可靠性

问题：`Remember()` 异步 goroutine 写 SQLite，存在 goroutine 堆积、进程退出丢失、embedding API 超时等风险。

方案：**有界写入队列 + graceful shutdown**

```go
type DualWriteBackend struct {
    primary   *PureMarkdownBackend
    secondary MemoryBackend
    writeCh   chan writeRequest  // 有界 channel，容量 256
    wg        sync.WaitGroup     // 等待 in-flight 写入完成
    ctx       context.Context
    cancel    context.CancelFunc
}
```

- 用 buffered channel（容量 256）替代裸 goroutine，防止堆积
- 单个 consumer goroutine 串行消费写入请求，避免 SQLite 写锁竞争
- channel 满时 drop + log warn（Markdown 已写成功，不阻塞主路径）
- `Close()` 方法：cancel context → drain channel → `wg.Wait()` 等待 in-flight 完成
- main.go 注册 shutdown hook 调用 `Close()`
- embedding API 调用设 10s timeout（独立于全局 30s），超时则跳过向量写入，仅写元数据 + FTS

### HA-2: SQLite WAL 模式 + 并发

问题：一个 writer（异步 goroutine）+ 多个 reader（搜索请求），WAL 模式下的锁行为。

方案：
- 开启 `PRAGMA journal_mode=WAL`（已有）
- `PRAGMA busy_timeout=5000`：写锁等待 5s 而非立即失败
- 读写分离：写入用独立 `*sql.DB`（`SetMaxOpenConns(1)`），搜索用共享 `*sql.DB`
- WAL 模式下读不阻塞写、写不阻塞读（SQLite 保证）
- 定期 `PRAGMA wal_checkpoint(TRUNCATE)` 防止 WAL 文件无限增长

### HA-3: FTS5 外部内容表同步

问题：`content=memory_chunks` 是 FTS5 外部内容表，INSERT/DELETE 必须手动同步，否则索引和数据不一致。

方案：**触发器自动同步**

```sql
-- 插入时自动同步 FTS
CREATE TRIGGER memory_chunks_ai AFTER INSERT ON memory_chunks BEGIN
    INSERT INTO memory_fts(rowid, content, tags) VALUES (new.id, new.content, new.tags);
END;

-- 删除时自动同步 FTS
CREATE TRIGGER memory_chunks_ad AFTER DELETE ON memory_chunks BEGIN
    INSERT INTO memory_fts(memory_fts, rowid, content, tags) VALUES('delete', old.id, old.content, old.tags);
END;

-- 更新时自动同步 FTS
CREATE TRIGGER memory_chunks_au AFTER UPDATE ON memory_chunks BEGIN
    INSERT INTO memory_fts(memory_fts, rowid, content, tags) VALUES('delete', old.id, old.content, old.tags);
    INSERT INTO memory_fts(rowid, content, tags) VALUES (new.id, new.content, new.tags);
END;
```

注意：memory_vec（sqlite-vec）不支持触发器，必须在 Go 代码中手动 INSERT/DELETE，与 memory_chunks 在同一事务中。

### HA-4: Embedding 维度变更

问题：用户切换 embedding provider（如 1536d → 768d），已有向量不兼容。

方案：
- `memory_chunks` 表新增 `embedding_model TEXT` 列，记录生成该向量的模型
- 启动时检测当前 provider 维度 vs `memory_vec` 表维度
- 维度不匹配时：
  1. 重建 `memory_vec` 表（`DROP + CREATE` 新维度）
  2. 后台 goroutine 逐条重新 embed 已有内容（从 memory_chunks 读 content）
  3. 重建期间搜索降级到 FTS5 only
- embedding cache 按 `(provider, model, text_hash)` 三元组去重，模型变更自动 miss

### HA-5: Markdown → SQLite 冷启动同步

问题：首次启用双写时，Markdown 中已有记忆但 SQLite 为空。

方案：
- 启动时检测 `memory_chunks` 行数 vs Markdown 文件数
- 差异超过阈值时，触发后台同步：遍历 Markdown memories → 逐条写入 SQLite + 生成 embedding
- 同步期间搜索走 Markdown fallback
- 同步完成后切换到混合搜索
- 同步进度通过 `Stats()` API 暴露

## 性能折衷

### PT-1: BM25 分数归一化

问题：FTS5 `bm25()` 返回负值（越小越好），sqlite-vec `distance` 是 0-2（cosine，0=完全相同）。两者量纲不同，直接加权不合理。

方案：**Go 层归一化**，不在 SQL 层做分数融合

```go
// 1. 分别查询，各取 limit*3 候选
vecResults := store.SearchVector(queryEmb, limit*3, 0)   // distance 0-2
ftsResults := store.SearchKeyword(queryText, limit*3)     // bm25 负值

// 2. 各自归一化到 [0, 1]
// vec: score = 1.0 - distance/2.0 (cosine distance 0-2 → similarity 0-1)
// fts: score = (rank - minRank) / (maxRank - minRank) 然后 1-x（min-max 归一化）

// 3. 合并去重 + 加权
// combined = vecScore * 0.7 + ftsScore * 0.3
// 双匹配 boost: combined *= 1.2 (cap 1.0)

// 4. 过滤 combined < 0.5
// 5. ImportanceScorer rerank
```

这比 SQL 层融合更准确，因为 BM25 的绝对值取决于语料库大小，需要 min-max 归一化。

SQL 层融合作为备选方案保留（适合数据量小、对精度要求不高的场景）。

### PT-2: sqlite-vec 向量量化

sqlite-vec 支持三种向量精度：

| 类型 | 语法 | 内存 (10K × 1536d) | 精度 | 适用场景 |
|------|------|---------------------|------|----------|
| `float[N]` | `embedding float[1536]` | ~60MB | 最高 | 默认，<10K 条 |
| `int8[N]` | `embedding int8[1536]` | ~15MB | 高（~1-3% 精度损失） | 10K-100K 条 |
| `bit[N]` | `embedding bit[1536]` | ~1.9MB | 中（需 rescore） | >100K 条 |

推荐策略：
- 默认 `int8[1536]`，4x 压缩，~15MB/10K 条，精度损失 ~1-3%，性能和内存的最佳平衡
- 配置项 `VectorQuantization: "float" | "int8" | "bit"`，可运行时切换
- 需要最高精度时切 `float`，需要极致压缩时切 `bit`（需 oversample + rescore）
- `bit` 量化需要 oversample + rescore 模式：

```sql
-- 双列存储：粗筛 + 精排
CREATE VIRTUAL TABLE memory_vec USING vec0(
    embedding float[1536],           -- 精确向量，用于 rescore
    embedding_coarse bit[1536]       -- 粗筛向量，用于快速召回
);
-- 先 bit 列 MATCH top-100 → 再 float 列 vec_distance_cosine() rescore → top-10
```

### PT-3: Embedding API 延迟 vs 搜索延迟

| 路径 | 延迟 | 说明 |
|------|------|------|
| 写入（缓存命中） | ~3ms | Markdown 写入 + SQLite 写入 |
| 写入（缓存未命中） | ~100-500ms | + embedding API 调用（异步，不阻塞用户） |
| 搜索（缓存命中） | ~5-10ms | embedding 缓存 + sqlite-vec + FTS5 |
| 搜索（缓存未命中） | ~100-510ms | + embedding API 调用（同步，阻塞搜索） |

搜索时 embedding API 调用是同步的（必须拿到 queryVec 才能搜索），这是主要延迟来源。

优化：
- embedding cache 命中率是关键，相同/相似 query 直接走缓存
- 对于高频 query（如 chat recall），可以在 `recallMemories()` 中预热缓存
- 搜索超时 3s，超时后降级到 FTS5 only

### PT-4: 跨平台 CGo 编译

sqlite-vec CGo binding 需要在以下平台编译：

| 平台 | 状态 | 注意事项 |
|------|------|----------|
| macOS arm64 | ✅ | 开发主力平台，`mattn/go-sqlite3` 已验证 |
| Linux amd64 | ✅ | 生产部署平台，CI 需安装 `gcc` |
| Linux arm64 | ✅ | ZimaBoard/树莓派，交叉编译需 `aarch64-linux-gnu-gcc` |
| Windows amd64 | ⚠️ | 需要 MinGW-w64，`mattn/go-sqlite3` 已支持 |

风险：sqlite-vec v0.1.6 是最新稳定版（2024-11），Go binding 可能有平台特定 bug。

缓解：
- CI 矩阵覆盖所有目标平台
- 编译失败时 build tag 降级到纯 Go fallback（`searchVectorFallback`）
- `//go:build cgo` 隔离 sqlite-vec 依赖

### PT-5: SQLite 单文件 vs 多文件

当前设计：所有数据在一个 `memory.db` 中（memory_chunks + memory_fts + memory_vec）。

优点：
- 事务一致性（三表在同一事务中写入）
- 简单，一个文件备份/恢复

缺点：
- memory_vec 的 WAL 写入量大（每条记忆 ~6KB 向量数据）
- FTS5 rebuild 时锁住整个 DB

替代方案（暂不实施，记录备选）：
- `memory.db`（memory_chunks + memory_fts）+ `memory_vec.db`（memory_vec）
- 通过 `ATTACH DATABASE` 关联
- 向量 DB 损坏不影响元数据和 FTS
