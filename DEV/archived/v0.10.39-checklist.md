## Overview

v0.10.39 is the next release record after the broader storefront, approval-clarity, localization, and shell follow-up wave documented in v0.10.38.

This time the center of gravity moves again:

- research-related entry points are being consolidated into one clearer `Research` family
- Blue gains a dedicated knowledge workspace instead of scattering knowledge maintenance behind lower-level flows
- automation grows a more explicit evolution console for skill revisions, evidence, and decision history
- chat recovery becomes more complete by restoring task state and pending interactions during bootstrap
- execution and sandboxing move toward one Blue-owned surface, with a first-class `blue exec`, tier-aware isolation, and shared runtime defaults for Blue/bluelib-family entrypoints
- local audit, failover, approval, and locale-integrity work continues to reduce operator friction and recovery ambiguity

This document intentionally focuses on the most recent local features and fixes now present in the working tree. Core version/reporting surfaces have been aligned to `0.10.39`, but the emphasis here remains on the user-facing themes rather than an exhaustive listing of every internal refactor.

## 8. Blue-Owned Exec Surface And Tiered Sandbox Routing ✅

- [x] Add a first-class `blue exec` command instead of leaving execution guidance as docs/runtime convention only
- [x] Support Blue-owned sandbox controls on `blue exec`, including `--sandbox` and `--sandbox-tier light|strong`
- [x] Route sandbox work through a two-tier model where low-risk work stays light and medium/high/critical work can request stronger isolation
- [x] Use one unified `network_toggle_supported` capability so platforms without network toggle support hide the control entirely
- [x] Wire Windows strong sandboxing to a Blue-managed Codex-based runtime that can be downloaded on demand
- [x] Move shared exec defaults into bootstrap/runtime helpers so Blue and bluelib-family entrypoints do not fork host-exec behavior
- [x] Keep sandbox-manager timeout policy authoritative by not forcing host-style default timeouts onto sandboxed exec requests

### What Landed

- [x] Blue now exposes a real `blue exec` command with docs-compatible command parsing, host execution by default, and optional sandbox routing when operators ask for it
- [x] Sandbox execution now distinguishes light versus strong isolation internally instead of pretending every platform has one identical backend
- [x] UI/API capability reporting was tightened around `network_toggle_supported`, so unsupported platforms simply stop showing a misleading network toggle
- [x] Windows strong-tier execution now has a Blue-managed Codex sandbox path that prefers configured/local binaries when available and can fall back to on-demand managed downloads only when strong isolation is actually needed
- [x] Shared runtime exec defaults were lifted into bootstrap so Blue CLI, bluelib-family entrypoints, and related support bundles stay aligned on host-exec behavior while sandboxed exec continues to defer to sandbox config
- [x] CLI/runtime verification was expanded around the new exec surface, including package-level coverage for command registration, host-vs-sandbox routing, and restart-loop behavior needed by the `server/cmd/blue` package tests

### Why It Matters

- [x] Execution now has one clearer Blue-owned surface instead of asking users to reason about lower-level sandbox tooling directly
- [x] Tiered routing gives Blue a practical path to stronger isolation per platform without breaking current light-backend support
- [x] Capability-driven network-toggle exposure is less confusing on platforms that cannot honor `NetworkEnabled`
- [x] Shared bootstrap defaults reduce drift between Blue CLI and other runtime entrypoints such as bluelib
- [x] Preserving sandbox-config authority over sandbox timeouts keeps runtime policy consistent instead of silently bypassing `security.sandbox.default_timeout`

## Release Summary

v0.10.39 should be read as the next candidate release record after v0.10.38, with the emphasis shifting toward workflow consolidation and operator recovery.

The main themes in this window are:

- a unified `Research` family that keeps mode-specific output while simplifying discovery

- a new `Evolution` console plus local `blue audit` tooling for skill iteration and operational visibility

- a Blue-owned `blue exec` surface plus tier-aware sandbox routing that prepares stronger per-platform isolation without exposing backend churn directly
- i18n naming/integrity cleanup plus failover-management follow-ups that improve maintainability and operational clarity
- bundle-based Harness dataset tooling and evaluation readiness work (datasets, specs, trajectory runs, and docs)
- new PDF/OCR extraction foundations that support richer knowledge and document-driven workflows

That gives the `0.10.39` record a clear story: fewer fragmented advanced workflows, better recovery context, steadier operator surfaces, and a more explicit Blue-owned path for controlled execution.
