# Typeless Card Rendering Optimization Report

**Date:** 2026-01-31
**Version:** v0.10.9
**Status:** Completed (Phase 4)

## Summary

Implemented a comprehensive rendering optimization system for typeless cards:
1. **Phase 1**: Hybrid rendering (functional + async components)
2. **Phase 2**: Render cache, Web Worker parsing, batch DOM updates, virtual scrolling
3. **Phase 3**: Parse result cache, component pooling, incremental parsing
4. **Phase 4**: Virtual scroll integration, shallow reactivity, component preloading

## Phase 1: Hybrid Rendering

### Problem Analysis

The original `TypelessCard.vue` had several performance issues:

1. **Static imports of all 28 components** - Every card type was imported at module load time
2. **Long v-if/v-else-if chain** - 28 conditional checks for every card render
3. **Vue component overhead** - Each card created a full Vue component instance

### Solution: Functional + Async Components


## Phase 2: Advanced Optimizations

### 1. Render Cache (LRU)

Implemented an LRU cache for rendered card HTML to avoid re-rendering identical cards:

```typescript
class RenderCache {
  private cache = new Map<string, CacheEntry>()
  private maxSize = 500        // Max cached cards
  private maxAge = 5 * 60 * 1000  // 5 minute TTL

  get(card: TypelessCard): string | null
  set(card: TypelessCard, html: string): void
}
```

**Benefits:**
- Repeated cards render instantly from cache
- Automatic eviction of old entries
- Content-based deduplication via hash

### 2. Web Worker Parsing

Moved heavy parsing logic to a Web Worker to avoid blocking the main thread:

```typescript
// Main thread
typelessParserWorker.parse(content, (result) => {
  // Handle parsed result
})

// Worker thread (typelessParser.worker.ts)
self.onmessage = (event) => {
  const result = parseTypelessContent(event.data.content)
  self.postMessage({ type: 'parsed', result })
}
```

**Benefits:**
- Main thread stays responsive during parsing
- Request deduplication (same content = single parse)
- Graceful fallback if workers unavailable

### 3. Batch DOM Updates

Batches multiple DOM updates into a single animation frame:

```typescript
class BatchDOMUpdater {
  queue(element: HTMLElement, html: string): void
  queueMany(updates: DOMUpdate[]): void
  flushSync(): void  // Force immediate flush
}

// Usage
batchDOMUpdater.queue(element1, html1)
batchDOMUpdater.queue(element2, html2)
// Both updates applied in next RAF
```

**Benefits:**
- Reduces layout thrashing
- Groups updates by parent element
- Single reflow per frame

### 4. Virtual Scrolling

Created a reusable virtual scroll component for long conversations:

```vue
<VirtualScroll
  :item-count="messages.length"
  :estimated-item-height="100"
  :overscan="3"
>
  <template #default="{ index, updateHeight }">
    <ChatMessage
      :message="messages[index]"
      @mounted="(h) => updateHeight(h)"
    />
  </template>
</VirtualScroll>
```

**Features:**
- Variable height item support
- Overscan for smooth scrolling
- Scroll-to-item API
- Resize observer integration

## Phase 3: Deep Optimizations

### 1. Parse Result Cache (LRU)

Caches the entire `ParsedContent` result to avoid re-parsing identical message content:

```typescript
class ParseResultCache {
  private cache = new Map<string, ParseCacheEntry>()
  private maxSize = 200        // Max cached results
  private maxAge = 5 * 60 * 1000  // 5 minute TTL

  get(content: string): ParsedContent | null
  set(content: string, result: ParsedContent): void
}
```

**Benefits:**
- Identical messages parse instantly from cache
- Deep clone prevents mutation issues
- Automatic eviction of old entries

### 2. Component Pool

Manages async-loaded card components, keeping them alive when scrolled out of view:

```typescript
class ComponentPool {
  private pools = new Map<string, PooledComponent[]>()
  private loadedComponents = new Map<string, Component>()

  async getComponent(cardType: string): Promise<Component | null>
  acquire(cardType: string): PooledComponent | null
  release(cardType: string, component: Component): void
  preload(cardTypes: string[]): Promise<void>
}
```

**Benefits:**
- Reuses component instances instead of creating/destroying
- Lazy loading with caching
- Automatic cleanup of idle components
- Preload API for common card types

### 3. Incremental Parsing

For streaming messages, only re-parses when new content might contain cards:

```typescript
export function parseTypelessContentIncremental(
  content: string,
  messageId: string
): ParsedContent {
  const state = incrementalStates.get(messageId)

  // If content is extension of previous, check if re-parse needed
  if (state && content.startsWith(state.lastContent)) {
    const newContent = content.slice(state.lastContent.length)

    // Skip re-parse if new content unlikely to have cards
    if (!mightHaveNewCards(newContent)) {
      return { text: state.lastResult.text + newContent, cards: state.lastResult.cards }
    }
  }

  // Full parse needed
  return parseTypelessContentInternal(content, 0)
}
```

**Benefits:**
- Streaming messages don't re-parse entire content
- Smart detection of card-like patterns
- Automatic state cleanup on unmount

- Smooth scrolling through thousands of messages

### 2. Shallow Reactivity for Messages

Changed messages store from `ref` to `shallowRef` to reduce reactivity overhead:

```typescript
// chat.ts store
import { shallowRef } from 'vue'

// Use shallowRef for messages to reduce reactivity overhead
const messages = shallowRef<Message[]>([])

// Updates require creating new array reference
messages.value = [...messages.value, newMessage]
```

**Benefits:**
- Reduced Vue reactivity tracking overhead
- Faster array updates (no deep proxy creation)
- Lower memory usage for large message lists

### 3. Component Preloading

Preload common card components on app initialization:

```typescript
// ChatView.vue onMounted
import { componentPool } from '@/utils/componentPool'

onMounted(async () => {
  // Preload common card components for better UX
  componentPool.preload(['progress', 'chart', 'gallery', 'link', 'file'])
  // ...
})
```

**Benefits:**
- Common components ready before user needs them
- Eliminates loading delay for first card render
- Background loading doesn't block UI
