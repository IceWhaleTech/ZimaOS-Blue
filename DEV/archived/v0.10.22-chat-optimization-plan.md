## 📊 Current CHAT Pipeline Analysis

### Request Flow
```
User Message
    ↓
Frontend API Call
    ↓
Backend Handler (chat.go)
    ↓
1. Security Check (Prompt Guard)
2. Provider Selection
3. Store User Message (DB Write)
4. Fetch History (DB Read - 50 messages)
5. Convert to LLM Format
6. Context Compaction
7. Build Chat Request
8. Call LLM Provider
9. Store Assistant Message (DB Write)
    ↓
Response to User
```

### Performance Bottlenecks Identified

| Bottleneck | Impact | Priority |
|------------|--------|----------|
| **DB Query (50 messages)** | Every request | 🔴 High |
| **Context Compaction** | CPU intensive | 🟡 Medium |
| **Provider Selection** | Repeated logic | 🟡 Medium |
| **Message Conversion** | Memory allocation | 🟢 Low |
| **Tool Definitions** | Repeated building | 🟢 Low |

---

## 🎯 Optimization Strategy

### Phase 1: Database Query Optimization (High Impact)
**Goal**: Reduce DB query overhead by 50-70%

#### 1.1 Conversation Context Cache ✅
- Cache last N messages per conversation
- Invalidate on new message
- TTL: 5 minutes
- **Expected**: 60-70% reduction in DB queries

#### 1.2 Smart History Fetching ✅
- Only fetch new messages since last request
- Maintain conversation state in memory
- **Expected**: 40-50% reduction in DB load

---

### Phase 2: Context Compaction Optimization (Medium Impact)
**Goal**: Reduce compaction overhead by 30-50%

#### 2.1 Compaction Result Cache ✅
- Cache compacted messages + summary
- Key: conversation ID + message count hash
- TTL: 10 minutes
- **Expected**: 30-40% faster for repeated contexts

#### 2.2 Incremental Compaction ✅
- Only re-compact when new messages exceed threshold
- Reuse previous summary
- **Expected**: 20-30% CPU reduction

---

### Phase 3: Request Processing Optimization (Low-Medium Impact)
**Goal**: Reduce request processing overhead by 20-30%

#### 3.1 Tool Definitions Cache ✅
- Cache tool definitions (rarely change)
- Rebuild only on registry update
- **Expected**: 10-15% faster request building

#### 3.2 Provider Selection Cache ✅
- Cache default provider for 1 minute
- Reduce repeated selection logic
- **Expected**: 5-10% faster provider selection

## 🚨 Risks & Mitigation

### Risk 1: Cache Invalidation Issues
**Mitigation**: Conservative TTLs, explicit invalidation on writes

### Risk 2: Memory Growth
**Mitigation**: LRU eviction, max cache size limits

### Risk 3: Stale Data
**Mitigation**: Short TTLs, invalidate on updates

### Risk 4: Increased Complexity
**Mitigation**: Clear documentation, comprehensive tests
