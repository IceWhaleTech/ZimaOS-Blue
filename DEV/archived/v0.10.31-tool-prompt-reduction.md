# v0.10.31 Tool→Skill Migration & Prompt Token Reduction — PRD

**Version**: 0.10.31
**Created**: 2026-02-26

---

## Overview

Currently, most capabilities are registered as **native Go tools** in `tools.Registry`, each injecting ~100-300 tokens of JSON Schema into every LLM request. Many of these tools also have parallel SKILL.md files — the LLM sees both the tool schema AND the skill description, doubling the token cost.

This PRD migrates most tools to a **skill + `blue` CLI subcommand** architecture:
- The LLM learns capabilities from SKILL.md (English only, in system prompt)
- The LLM invokes them via `exec` (calling `blue <subcommand> ...`)
- `exec` itself can also be removed — its SKILL.md gets elevated priority in the system prompt
- A **stdout card protocol** (streaming + non-streaming) enables CLI subcommands to emit typeless cards
- `process` is absorbed into `exec` as sub-actions
- Frontend card components updated for skill-based tool rendering

**Target**: Reduce from ~12 tool definitions (~4,000 tokens) to 0 native tools. All capabilities become skills with `blue` CLI subcommands. The `exec` skill has elevated priority in the system prompt as the universal invocation primitive.

```
  → exec parses stdout, forwards cards to frontend via CardEmitter
  → exec returns JSON result to LLM
```

## 1. Stdout Card Protocol (Streaming + Non-Streaming)

**Problem**: Tools like `analyze`, `browser`, `ui_reviewer`, and `reminder` currently emit typeless cards via Go's in-process `CardEmitter`. When migrated to CLI subcommands, they run as child processes with no direct access to the SSE stream.

**Solution**: A stdout-based card protocol with two modes:
- **Streaming mode**: Cards emitted line-by-line during execution, forwarded to SSE in real-time
- **Non-streaming mode**: Cards accumulated and returned as part of the final JSON result

### 1.1 Protocol Format

```
__CARD__{"type":"analyze-progress","step":"data_collection","name":"Gathering data","status":"running"}__END__
```

- Prefix: `__CARD__`
- Payload: JSON object (same schema as current `EmitCard()` calls)
- Suffix: `__END__`
- One card per line (no multiline JSON)
- Card lines are stripped from the final stdout result returned to the LLM

### 1.2 Streaming Mode (Real-Time SSE)

When exec runs a `blue` subcommand, stdout is read **line-by-line in a goroutine**:

```go
// exec stdout scanner — streaming card forwarding
scanner := bufio.NewScanner(stdoutPipe)
for scanner.Scan() {
    line := scanner.Text()
    if cardJSON, ok := extractCard(line); ok {
        EmitCard(ctx, cardJSON)  // → SSE delta immediately
        continue
    }
    outputBuf.WriteString(line + "\n")
}
```

Cards appear in the frontend **as they are emitted** — not after the command finishes. This preserves the current UX for analyze progress, browser navigation, etc.

### 1.3 Non-Streaming Mode (Batch)

For short-lived commands (e.g., `blue memory search`), cards are accumulated and returned as part of the JSON result. The exec tool detects this automatically — if the command exits within 500ms, cards are batched.

### 1.4 Go Helper for Subcommands

```go
// internal/cardproto/emit.go — shared by all blue subcommands
package cardproto

func EmitCard(card map[string]interface{}) {
    data, _ := json.Marshal(card)
    fmt.Fprintf(os.Stdout, "__CARD__%s__END__\n", data)
}

func EmitProgress(cardType, step, name, status string) {
    EmitCard(map[string]interface{}{
        "type": cardType, "step": step, "name": name, "status": status,
    })
}
```

### 1.4 Card Types Preserved

All existing card types continue to work unchanged:
- `analyze-progress` (step/name/status)
- `browser-progress` (step/name/status/url)
- `ui-review-progress` (step/name/status/url/score)
- `alert` (variant/title_key/message)

Frontend rendering is unchanged — cards arrive via the same SSE delta mechanism.

## 2. `ask_user_question` → Skill + IPC Bridge

**Problem**: `ask_user_question` requires bidirectional IPC — push question to frontend via SSE, block until user responds via REST. A simple CLI subcommand can't do this.

**Solution**: `blue ask` subcommand uses the existing `QuestionManager` via a local HTTP call to the running Blue server.

### 2.1 CLI Subcommand Design

```bash
blue ask --questions '[{"question":"Which approach?","options":["A","B"]}]' --timeout 120
```

**Execution flow**:
1. `blue ask` POSTs to `http://localhost:<port>/api/v1/ask-user-question` with the questions JSON
2. Server-side `QuestionManager.AskQuestions()` publishes SSE event, blocks for answer
3. User answers in frontend → `POST /api/v1/ask-user-question/:id/answer`
4. `QuestionManager` unblocks, returns answers to the internal API
5. `blue ask` receives response, prints JSON to stdout
6. `exec` returns the JSON to the LLM

### 2.2 Server-Side Endpoint

Add `POST /api/v1/ask-user-question` (new endpoint, distinct from the answer endpoint):
- Accepts: `{ "questions": [...], "timeout": 120, "user_id": "..." }`
- Calls `QuestionManager.AskQuestions()` (same logic as current tool)
- Returns: `{ "answers": {...} }` or timeout error
- Auth: Same API key auth as other endpoints

### 2.3 Silent Mode

When `blue ask` detects non-interactive context (no TTY, or `--silent` flag), it auto-answers with first option — same as current `AskUserQuestionTool` silent mode.

### 2.4 Card Emission

`blue ask` emits a card via stdout protocol before blocking:
```
__CARD__{"type":"ask-user-question","status":"waiting","questions":[...]}__END__
```

## 3. Absorb `process` into `exec`

**Rationale**: `process` manages exec sessions (list/poll/log/kill). It shares the same `SessionRegistry` as exec. Making it a separate tool wastes ~100 tokens.

### 3.1 New Exec Sub-Actions

Add to exec's parameter schema:

| Action | Replaces | Behavior |
|--------|----------|----------|
| `exec --list-sessions` | `process list` | List running/finished sessions |
| `exec --poll <session_id>` | `process poll` | Get pending output |
| `exec --log <session_id>` | `process log` | Get full output |
| `exec --kill <session_id>` | `process kill` | Terminate session |

### 3.2 Remove ProcessTool

- Remove `ProcessTool` from [builtin.go](server/internal/tools/builtin.go)
- Move session management logic into `ExecTool.Execute()` as action branches
- Update exec's SKILL.md with session management docs

**Savings**: ~100 tokens.

Each migrated tool becomes a `blue` CLI subcommand. The subcommand:
- Connects to the running Blue server via local HTTP API (or direct DB access where appropriate)

- Exits with 0 on success, non-zero on error

## 9. Risk & Mitigation

| Risk | Impact | Mitigation |
|------|--------|------------|
| LLM forgets to use `exec` for skills | High — capability loss | System prompt explicitly says "invoke skills via exec" |
| Card protocol parsing errors | Medium — broken progress UI | Strict prefix/suffix matching, malformed lines pass through as normal output |
| `blue` subprocess startup latency | Medium — slower than in-process | `blue` is already running as server; subcommands connect via HTTP, not cold start |
| `ask_user_question` timeout via HTTP | Medium — longer chain | Local HTTP call adds <5ms; timeout is user-facing (2min), not network |
| Backward compat with saved conversations | Low — old tool_use in history | Old tool names in history are harmless; LLM won't re-call them |
| `blue` binary not found | High — all skills broken | Use `os.Executable()` as primary path; fail loudly with clear error |

## 10. Success Metrics

- **Tool schema tokens**: Target 0 tokens (down from ~4,000). 100% reduction.
- **Total system prompt + skills**: Target ≤3,000 tokens for a typical request.
- **Card rendering**: All existing card types render correctly via stdout protocol (streaming + non-streaming).
- **Skill invocation success rate**: ≥95% of skill calls via exec succeed on first attempt.
- **Latency overhead**: <50ms additional latency from subprocess invocation vs in-process tool call.
- **Streaming card latency**: Cards appear in frontend within 100ms of emission by subcommand.
