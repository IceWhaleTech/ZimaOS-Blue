## Overview

v0.10.33 was the release where the early harness-group backend became product-visible. The main outcome was not a single isolated feature, but a cluster of operational capabilities landing together:

- Harness groups became storable, dispatchable, and inspectable from the web UI
- Browser approvals and scanner settings became explicit user-facing controls
- Productivity tools expanded beyond general-purpose chat helpers into calendar and email actions
- The skill-market and selector surfaces grew from lightweight scaffolding into a more obvious product area
- Chat/runtime safety and recovery coverage were expanded to support the broader surface safely

## Strategic Context

The planning work around this release window points to four larger themes, and v0.10.33 appears to implement the first concrete slice of each:

- Harness was being redefined as a unified runtime control plane for grouped runs, permissions, orchestration, and evaluation. This release makes that direction product-visible through group storage, dispatch, scoring, handlers, and the first dedicated group-management UI.
- The skills marketplace was being expanded from a lightweight surface into a real backend domain with service, storage, ranking, and security responsibilities. This release does not complete that vision, but it clearly establishes the first substantial backend shape.
- Tool and skill selection were being pushed away from loose keyword matching toward more structured profiles and routing signals. The selector/profile work in this release aligns with that direction.
- Product pressure was shifting toward stronger direct-answer quality, better productivity completion, and benchmark-driven fixes. The calendar/email tool additions and benchmark runner work fit that push.

## Implementation Notes

### Backend Runtime Notes

- The harness package gained the minimum set of primitives needed for group-oriented workflows: persistence, dispatch, scoring, and route handling.
- The bootstrap layer picked up more explicit route and startup tracing behavior, which helped support the broadened security and harness surfaces.
- The chat runtime grew stronger guardrails around grounding, tool fallback, and ownership behavior while the product surface expanded.

### Tooling and Skill-Market Notes

- `server/internal/tools/calendar.go` and `server/internal/tools/email.go` marked a shift toward more task-oriented built-in tools.
- Selector logic was expanded both in ClaudeCode-facing selection and the runtime tool selector so the larger tool inventory remained usable.
- The skill-market surface moved beyond a thin placeholder and started to look like a first-class backend subsystem with service, store, parsing, ranking, and security layers.

### Web Product Notes

- `HarnessGroupsView` made harness execution visible as a grouped operational flow instead of an internal-only capability.
- `HomeView`, `SettingsView`, and `SecurityView` were all adjusted to expose the growing runtime surface more clearly.
- `SkillStoreTab`, `SkillTab`, and `ToolTab` were reworked in parallel with the backend skill-market changes so discovery and management stayed usable.

## User-Facing Outcomes

- Harness runs became visible as grouped operational objects rather than purely internal backend state.
- Browser approvals became easier to reason about from the product UI, reducing the gap between security policy and day-to-day use.
- Home and settings surfaces exposed more runtime state directly, making the system feel more inspectable and less opaque.
- Productivity capabilities expanded in a way users could plausibly feel immediately: calendar/email-oriented tasks became more native to the runtime.
- Skill discovery and management started to look more like a product subsystem than a hidden extension mechanism.

## Follow-up Signals

- A fuller harness control plane with explicit session trees, approvals, sandbox policy, and replayable evaluation was planned, but v0.10.33 only shows the earlier group-management slice.
- The marketplace plan envisioned search, install, update, telemetry, and stronger security pipelines. This release mostly established the backend domain and UI direction rather than the complete product shape.
- The selector plan implied stronger ambiguity handling and conflict-aware routing. v0.10.33 appears to lay profile groundwork, but not the full plan in one release.

## Deferred or Still In Motion

- Harness was not yet presented as a unified user task layer; this release mainly exposed grouped operational management rather than a broader projection model.
- The marketplace backend direction was visible, but a fully mature search/install/update loop was not yet the center of the user-facing experience.
- Selector/profile work had clearly started, but routing still appears to have been in a transitional state rather than a fully finished architecture.
- Productivity tooling expanded, but deeper end-to-end workflows such as more polished summary, triage, and orchestration experiences were still developing.
