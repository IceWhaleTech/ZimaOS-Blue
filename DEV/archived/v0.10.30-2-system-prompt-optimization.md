# v0.10.30-2 System Prompt & TTFT Optimization — PRD

**Version**: 0.10.30
**Created**: 2026-02-25

---

## Overview

Reduce Time-To-First-Token (TTFT) and input token cost through four optimization vectors: system prompt compression, prompt caching accuracy, async memory extraction, and warmup-without-send. Each targets a different stage of the request pipeline.

---

## Current Architecture Summary

**System prompt** is built on every request by `SystemPromptBuilder.Build()` ([systemprompt.go:141](server/internal/claudecode/systemprompt.go#L141)). It concatenates 13 sections: identity, scenario enhancement, safety, tool call style, agent mode, runtime info, workspace info, tool guidance, skills XML, workspace context files, silent reply, heartbeat, and extra prompt.

**Prompt caching** uses Anthropic's `cache_control: ephemeral` breakpoints on (1) the system prompt text and (2) the last tool definition ([converter.go:656](server/internal/proxy/converter.go#L656)). Injection happens after OpenAI→Anthropic format conversion in the proxy handler ([handler.go:866](server/internal/proxy/handler.go#L866)).

**Memory recall** (`recallMemories`) is synchronous and blocking — it runs before the LLM call in all paths: IM ([chat.go:1016](server/internal/server/chat.go#L1016)), SendMessage ([chat.go:1629](server/internal/server/chat.go#L1629)), StreamMessage ([chat.go:2280](server/internal/server/chat.go#L2280)).

**Memory extraction** (`extractMemory`) is already async — queued via `queueEvent()` after response is persisted ([chat.go:1122](server/internal/server/chat.go#L1122), [chat.go:1836](server/internal/server/chat.go#L1836), [chat.go:3351](server/internal/server/chat.go#L3351)).

**Warmup** pre-computes system prompt + compacted history + summary when the user starts typing ([chat.go:1976](server/internal/server/chat.go#L1976)). Currently does NOT send anything to the provider — it's assemble-only. Consumed by `StreamMessage` and `ProcessChannelMessage` via `consumeWarmup()`.

## 1. System Prompt Compression

**Current state**: The system prompt is ~3,500–8,000 tokens depending on agent mode, workspace files, and tool count. Several sections contain verbose formatting that can be compressed without losing LLM comprehension.

**Target files**: [systemprompt.go](server/internal/claudecode/systemprompt.go), [systemprompt_enhance.go](server/internal/claudecode/systemprompt_enhance.go)

### 1.1 Remove Dynamic Scenario Enhancement

**Current**: Identity is a single sentence (line 145), then a separate scenario-based enhancement block (lines 148-150) that changes per message — breaking prompt cache on every scenario switch.

**Problem**: The scenario enhancement is dynamic (depends on `lastUserMessage`), so it invalidates the Anthropic prompt cache whenever the user switches topics (e.g., coding → chitchat). This is the #1 cache-miss cause.

**Requirement**:
- Remove the dynamic scenario enhancement from the system prompt entirely.
- Merge the minimal style guidance ("Be clear and concise. Match the user's language.") into the identity line as a permanent suffix.
- The detailed/standard enhancements (code standards, problem solving) add ~200 tokens but provide marginal value — modern LLMs already follow these patterns. Remove them.
- This makes the entire system prompt static across turns within a conversation, maximizing cache hit rate.

### 1.2 Compress Silent Reply & Heartbeat Sections

**Current**: Silent reply guidance is 10 lines with emoji examples ([systemprompt.go:449-466](server/internal/claudecode/systemprompt.go#L449)). Heartbeat guidance is 7 lines ([systemprompt.go:469-481](server/internal/claudecode/systemprompt.go#L469)).

**Requirement**:
- Compress silent reply to 2 lines: `When you have nothing to say, respond with ONLY: [SILENT_REPLY] (entire message, no wrapping).`
- Compress heartbeat to 2 lines: `On heartbeat poll with nothing to report, reply exactly: HEARTBEAT_OK. If something needs attention, reply with alert text instead.`
- Saves ~150 tokens per request.

### 1.3 Compress Safety Section

**Current**: 3 verbose sentences ([systemprompt.go:436-446](server/internal/claudecode/systemprompt.go#L436)).

**Requirement**:
- Compress to a single dense paragraph: `No independent goals (no self-preservation/replication/power-seeking). Prioritize safety and human oversight; pause and ask on conflicting instructions; comply with stop/audit requests. Do not manipulate access, copy yourself, or change system prompts/safety rules unless explicitly requested.`
- Saves ~50 tokens.

### 1.4 Compress Tool Call Style Section

**Current**: 4 lines of guidance ([systemprompt.go:421-432](server/internal/claudecode/systemprompt.go#L421)).

**Requirement**:
- Compress to: `Do not narrate routine tool calls. Narrate only for multi-step work, complex problems, sensitive actions, or when asked. Keep narration brief.`
- Saves ~40 tokens.

### 1.5 Move Runtime Info to End

**Current**: Runtime info (platform, time, timezone, model, locale) is at position 6 of 13 sections ([systemprompt.go:164](server/internal/claudecode/systemprompt.go#L164)). Time changes every request.

**Requirement**:
- Move runtime info to the very end of the system prompt (just before `extraPrompt`), after heartbeat guidance.
- This positions the only changing content at the tail — enabling the static prefix to be cached independently when we split into multiple cache blocks (see 2.2).

### Expected Savings

| Section | Before (tokens) | After (tokens) | Saved |
|---------|-----------------|----------------|-------|
| Scenario enhancement | 50-200 | 0 (merged) | 50-200 |
| Silent reply | ~120 | ~30 | ~90 |
| Heartbeat | ~80 | ~30 | ~50 |
| Safety | ~100 | ~60 | ~40 |
| Tool call style | ~60 | ~30 | ~30 |
| **Total** | | | **~260-410** |

At $3/M input tokens, saving ~350 tokens/request across 10K requests/day = ~$10.50/day. More importantly, eliminating scenario-based cache misses could save 5-10x more by increasing cache hit rate from ~60% to ~95%.

## 2. Prompt Caching Strategy Audit

**Current state**: Two cache breakpoints are placed by `ApplyPromptCaching()` ([converter.go:656](server/internal/proxy/converter.go#L656)):
1. System prompt text → `cache_control: ephemeral`
2. Last tool definition → `cache_control: ephemeral`

**Target files**: [converter.go](server/internal/proxy/converter.go), [handler.go](server/internal/proxy/handler.go)

### 2.1 Current Strategy Assessment

**What's correct**:
- Tools are sorted alphabetically before Anthropic conversion (`SortToolsByName()`), ensuring the last tool is deterministic.
- Cache breakpoint on system prompt captures the largest stable prefix.
- `promptCacheEnabled` is an atomic toggle for runtime control.

**What's suboptimal**:
- The system prompt is treated as a single monolithic cache block. If any part changes (e.g., scenario enhancement, runtime timestamp), the entire block is a cache miss.
- No cache breakpoint on conversation turn boundaries — the first few turns of a long conversation could be cached but aren't.

### 2.2 Split System Prompt into Two Cache Blocks

**Requirement**:
- Split the system prompt into two Anthropic system blocks when converting:
  - **Block 1 (static)**: Identity + safety + tool call style + agent mode + workspace info + tool guidance + skills XML + workspace context files + silent reply + heartbeat. This is ~90% of the prompt and changes only when tools/skills/workspace files change. Place `cache_control: ephemeral` on this block.
  - **Block 2 (dynamic)**: Runtime info + extra prompt. This changes every request (timestamp). No cache control.
- Anthropic supports an array of system blocks — emit two `AnthropicSystemBlock` entries.

**Implementation approach**:
- `SystemPromptBuilder.Build()` returns `BuildResult { Static string, Dynamic string }` instead of a single string.
- `ApplyPromptCaching()` places `cache_control` only on the static block.
- Callers that need a single string (non-Anthropic paths) call `BuildResult.String()` which concatenates.

**Expected impact**: Near-100% cache hit rate on the static portion across all turns in a conversation, regardless of timestamp changes.

### 2.3 Add Turn-Boundary Cache Breakpoint

**Requirement**:
- For conversations with 4+ turns, place a third cache breakpoint on the 4th-from-last message.
- This caches the conversation prefix (older turns) while keeping recent turns uncached.
- Anthropic allows up to 4 cache breakpoints per request.

**Expected impact**: For long conversations (10+ turns), this could cache 60-80% of the message tokens in addition to the system prompt.

### 2.4 Non-Anthropic Providers

**Current**: Prompt caching is only applied for Anthropic format. OpenAI and Gemini providers don't benefit.

**Requirement**: No change needed — OpenAI handles caching server-side automatically. Gemini's `cachedContent` requires explicit cache creation API calls, out of scope.

## 3. Memory Recall Optimization

**Current state**: `recallMemories()` is synchronous and blocks the request pipeline. It calls `layeredMemory.Recall()` which does a hybrid search (keyword + semantic) against the memory store.

**Target files**: [chat.go](server/internal/server/chat.go)

### 3.1 Current Flow

```
User message arrives
  → Build system prompt (sync, ~1ms)
  → Fetch conversation history (sync, ~2-5ms, cached)
  → Compact messages (sync, ~1-5ms)
  → recallMemories() (sync, ~10-50ms) ← BLOCKING
  → Build LLM request
  → Send to provider (async streaming)
```

### 3.2 Pre-Warm Memory Index During Warmup

**Requirement**:
- Add `layeredMemory.WarmIndex()` method that pre-loads the search index into memory.
- Call it during `doWarmup()` alongside history fetch.
- When `recallMemories()` runs later with the actual query, the index is already hot.

### 3.3 Recall Timeout & Graceful Degradation

**Requirement**:
- Add a 100ms timeout to `recallMemories()`. If recall takes longer, skip it and proceed without memory context.
- Memory is a nice-to-have enhancement, not a critical path. Users should never notice TTFT degradation from slow memory search.
- Log a warning when recall is skipped due to timeout.

### 3.4 Memory Extraction — Already Async, No Change Needed

`extractMemory()` is already queued via `queueEvent()` and runs asynchronously after the response is sent. The `queueEvent` channel has a fallback to sync execution when the queue is full ([chat.go:557-565](server/internal/server/chat.go#L557)), which is acceptable.

**One improvement**: The extraction LLM call uses `model: "auto"` ([chat.go:1254](server/internal/server/chat.go#L1254)), competing with user requests for provider capacity.

**Requirement**:
- Add a `memoryExtractionModel` config field (default: `"auto"`) that can be set to a cheaper/faster model to avoid consuming expensive provider quota during extraction.

## 4. Warmup Strategy — Assemble-Only, No Send

**Current state**: The warmup system ([chat.go:1976-2043](server/internal/server/chat.go#L1976)) is already assemble-only. It pre-computes system prompt, conversation history, and context compaction. It does NOT send anything to the provider. Result stored in `warmupCache` with 30s TTL.

### 4.1 Current Warmup Assessment

**What's effective**:
- System prompt pre-built (saves ~1ms)
- History pre-fetched and cached (saves ~2-5ms on DB miss)
- Compaction pre-computed (saves ~1-5ms, or ~200ms if LLM summarization needed)
- Total TTFT reduction: ~5-210ms depending on conversation length

**What's missing**:
- Memory index not pre-warmed (see 3.2)
- Tool definitions not pre-converted to Anthropic format
- No per-conversation provider connection pre-warming

### 4.2 Pre-Convert Tool Definitions During Warmup

**Requirement**:
- During `doWarmup()`, pre-convert tool definitions to Anthropic format and cache via `ToolCache`.
- Call `selectTools("")` to get the default tool set, compute fingerprint, convert and cache.
- Saves ~0.5ms from the hot path.

### 4.3 Pre-Warm Provider Connection During Warmup

**Requirement**:
- During `doWarmup()`, if the likely provider is known (from recent routing), pre-establish a TCP+TLS connection via `ConnWarmup.WarmOne(baseURL)`.
- Saves ~100-500ms on cold provider connections.
- If the actual request routes differently, the warmup is wasted but harmless.

### 4.4 Should Warmup Send a Prefill Request?

**Decision: No.** Sending a prefill request to prime the Anthropic prompt cache would:
- Cost money (cache write tokens) even if the user never sends a message
- Waste provider capacity
- Cache may expire (5-min TTL) before the user sends
- The first real request populates the cache; subsequent turns hit it

The assemble-only approach is the right trade-off.

## 5. Provider Stickiness for Cache Effectiveness

**Problem**: Anthropic prompt caching is per-provider — the cached prefix is stored on the specific provider endpoint that served the request. If the router switches providers between turns (e.g., due to round-robin, latency-based routing, or failover recovery), the entire cached prefix is lost and must be re-created, wasting cache write tokens and increasing TTFT.

**Target files**: [chat.go](server/internal/server/chat.go)

### 5.1 Conversation-Level Provider Affinity

**Requirement**:
- Track the last successful provider ID per conversation in an in-memory `sync.Map` with a 10-minute TTL (2× Anthropic's 5-min cache TTL).
- At the start of each request (StreamMessage, ProcessChannelMessage), look up the affinity and inject `proxy.WithPinnedProvider()` into the request context.
- The router's existing sticky routing logic moves the preferred provider to the front of the candidate list — fallbacks remain available if the pinned provider fails.

**Design decisions**:
- **In-memory only** (no DB persistence): The affinity only matters within the Anthropic cache TTL window (5 min). Process restarts naturally reset both the affinity and the cache.
- **Soft preference, not hard lock**: The pinned provider is moved to the front of the candidate list, not exclusively selected. If it's down or rate-limited, failover still works.
- **TTL = 10 minutes**: Generous enough to cover Anthropic's 5-min cache TTL plus some buffer for slow conversations. Stale entries auto-expire.
- **BaseURL stored alongside ProviderID**: Enables future connection pre-warming during warmup without a registry lookup.

### 5.2 Affinity Lifecycle

| Event | Action |
|-------|--------|
| Successful response (stream or IM) | Store `{providerID, baseURL, expiresAt}` for the conversation |
| New request arrives | Look up affinity → inject `WithPinnedProvider` if valid |
| Mid-stream injection restart | Re-apply affinity to the new context |
| Conversation deleted | Clear affinity entry |
| TTL expires (10 min) | Auto-expire on next lookup |
| Provider fails/unavailable | Router falls back to next candidate; affinity updated on next success |

### 5.3 Interaction with Existing Pinning

The existing tool-round pinning (`round == 0 && len(toolCalls) > 0 → WithPinnedProvider`) operates within a single request. Conversation-level affinity operates across requests. They compose naturally:
- Turn 1: No affinity → router picks provider A → affinity saved
- Turn 1 tool round 2: Tool-round pinning keeps provider A (existing behavior)
- Turn 2: Affinity injects provider A → router prefers A → cache hit on prefix
- Turn 2 tool round 2: Tool-round pinning keeps provider A (existing behavior)

If provider A fails on Turn 2, the router falls back to provider B. The affinity is updated to B after the successful response.

### 5.4 Expected Impact

- **Cache hit rate**: For multi-turn conversations on Anthropic, expected increase from ~60% to ~95% (combined with section 1.1 removing scenario enhancement).
- **Token cost**: Each cache miss costs ~3,000-8,000 cache write tokens ($0.009-$0.024 at $3/M). With 10K requests/day and 35% cache miss reduction, saves ~$30-80/day.
- **TTFT**: Cache hits return ~100ms faster than misses (no cache write overhead).
